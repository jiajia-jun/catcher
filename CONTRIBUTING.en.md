# Contributing to Catcher

[简体中文](CONTRIBUTING.md) | [English](CONTRIBUTING.en.md)

Issues and pull requests are welcome. Catcher is a Windows desktop app (Wails v2 + Go + Vue 3) that aggregates assignments from Yuketang, Chaoxing, TronClass, and Pigai into one local window.

Before contributing, make sure your change fits the project's positioning: **local-first, cloud AI requires explicit opt-in and confirmation of each request's scope, and platform login or anti-abuse mechanisms are never bypassed**.

## Design principles

Catcher has **two ground rules**; changes are reviewed against them.

### Local-first

- Assignment records and plans persist in the local data directory (`data/`); no cloud account system or telemetry. Optional AI request scope requires separate confirmation
- Platform passwords, login sessions, logs and databases are not sent out; optional cloud AI sends only previewed and confirmed questions, selected assignment metadata and availability
- Except for fetching platform data and checking for updates, the app opens and works offline
- Local-first also means **failures must be explicit**: better to error than to silently return an empty list
- Backup, migration, and uninstall revolve around this directory only; no remote service is involved

### No third-party

- No third-party backend, BaaS, serverless functions, analytics SDK, crash reporting, or CDN dependency
- The project has Go backend logic, but it runs locally only; **no server is deployed**, and no relay, storage, or account service is provided
- No local port listening, no background service, no browser extension required; requests are only made when the user acts
- Outbound requests target assignment platforms and GitHub Releases; explicitly enabled AI connects directly to the user's configured provider without a project relay
- Sessions and credentials stay local; passwords and authorization codes are encrypted with DPAPI and never pass through a relay
- The update check only queries GitHub Releases for the version number; nothing is downloaded or executed, and download pages open in the system browser

## Before you start

- Search issues and existing PRs first to avoid duplicate work
- For new features or larger changes (new platform, data model, `sender` behavior), **open an issue first** and agree on the approach
- **Small fixes** and **interface docs** can go straight to a PR
- Be friendly and stay on topic

## Prerequisites

- Windows 10/11 (session and password encryption rely on DPAPI; on non-Windows platforms it only returns `ErrUnsupported`)
- Go 1.27.1 (matching `go.mod` and CI)
- Node 24 / npm 11
- Wails CLI v2.13.0
- WebView2 Runtime (handled by the installer; portable builds require it to be present, bundled with Windows 11)

```bash
go install github.com/wailsapp/wails/v2/cmd/wails@v2.13.0
wails version
```

> **Do not upgrade Go casually**: Wails v2.13.0 fails to generate bindings under Go 1.27.3, so CI pins 1.27.1.

## Local development

```bash
wails dev                      # run frontend and backend; frontend hot reload; data goes to data/ at the repo root
wails build                    # output: build/bin/Catcher.exe
go build ./...                 # compile Go only (requires at least a placeholder in frontend/dist)
go test ./...                  # all unit tests
go vet ./...                   # static checks
go fmt ./...                   # formatting
cd frontend && npm run build   # vue-tsc type check + bundle
```

- There is no Makefile; run the commands directly
- In dev mode the data directory is `data/` at the repo root; release builds use `data/` next to the executable
- `frontend/wailsjs/` is generated by Wails; **do not edit it by hand**. Rerun `wails dev` or `wails build` after changing Go bindings

## Branching model

**`main` is the only long-lived branch** and must always be releasable.

1. Cut a short-lived branch from the latest `main`, named `<type>/<short-kebab-description>`, where `type` matches the commit prefix
   - `feat/homework-filter`
   - `fix/qr-countdown`
   - `docs/sender-contract`
2. Commit on the branch, splitting work into small commits by feature
3. Push and open a PR targeting `main`
4. Rebase the branch onto the latest `main` before merging
5. Always merge with **Rebase and merge**, then delete the remote branch; the local branch is optional

> **Note: do not commit directly to `main`**, and do not use merge commits (they break linear history).

## Commit messages

This repository writes commit messages in Chinese, using conventional prefixes with Chinese scopes:

```text
feat(首页): 增加按课程搜索
fix(学习通): 详情页 302 不再误判为登录失效
docs(接口): 补充扫码状态表
refactor(service): 拆分刷新任务
test(config): 补数据目录解析用例
chore(发布): 版本号改为 1.3.0
```

- Keep it concise: **title only**; add one or two lines of rationale if needed
- **One commit, one change**; do not mix in unrelated formatting or drive-by refactors

## Contributor credit

**Good ideas count as contributions too!** If a proposal from your issue or discussion is adopted and implemented by a maintainer, **we will credit you in the corresponding release commit**:

```text
Co-authored-by: Your Name <you@example.com>
```

To be credited, include the name and email you want to use in the issue; a GitHub noreply address is fine if you prefer not to share your real one.

## Code conventions

Layer dependency direction:

```text
main.go -> cmd/app -> internal/handle -> internal/service -> internal/domain
internal/infra -> internal/domain
all layers -.-> pkg
```

See [docs/架构.md](docs/架构.md) for layer responsibilities and `pkg` constraints. Hard rules:

- `domain` is the innermost layer and does not depend on outer layers; `infra` implements the ports defined by `domain`, and wiring happens in `cmd/app`
- `pkg` **must not** import anything under `internal/` or `cmd/`
- `handle` is the Wails binding layer and does not accept `http.Request`; the project has no local HTTP server, port, or CORS
- Wails method arguments and results go in `internal/dto`; do not expose domain entities directly
- Platform adapters live in `internal/infra/bridge/<platform>`; each adapter owns its own `Sender` so rate limits stay independent
- Platform IDs **must always be `int64`**, never `float64` (Chaoxing course IDs will silently mismatch otherwise)
- `sender` holds no cookies, does not use a cookiejar, does not follow redirects automatically, does not retry, and does not parse business responses. Read [internal/infra/sender/README.md](internal/infra/sender/README.md) before changing `Do`
- Handle time fields according to each platform's doc; do not apply one universal rule. **Failures must be explicit**: an expired login must not look like "no assignments today"
- Comments and docs are written in Chinese

Explain the reason before adding a dependency; prefer the standard library.

## Data and security

- **Do not commit real credentials**. `data/`, `catcher.json`, `draft/`, and `CLAUDE.md` are in `.gitignore`
- Passwords and sessions are encrypted with DPAPI before storage; they **must not appear in logs, events, or DTO return values**
- Do not log the values of `Cookie`, `Set-Cookie`, or `Authorization`; `pkg/logger` provides redaction helpers
- Packet-capture exports and raw response archives are redacted by default; **never paste unredacted exports into issues, PRs, or commits**
- Interface docs are published in `docs/接口文档/`. When adding or editing them, **replace real phone numbers, accounts, cookies, tokens, course IDs, course names, activity IDs, and assignment titles with placeholders**; follow the existing docs
- Mark unverified platform behavior as "unverified"; **do not present guesses as facts**, and do not remove existing warnings
- **Do not submit changes that bypass login or anti-abuse mechanisms, mass-register accounts, or share accounts**

## Tests

- Unit tests live next to the package under test, named `*_test.go`
- Platform adapter tests use fixed fixtures or local HTML/JSON and **never hit real sites**; use fake data for credential-related cases
- When changing `sender`, time parsing, deduplication keys, or status mapping, **add the corresponding edge cases**
- Run at least the following before opening a PR:

```bash
go test ./...
go vet ./...
```

- If you changed the frontend, also run `cd frontend && npm run build` (includes the `vue-tsc` type check)
- If you changed user-visible behavior, describe reproduction and verification steps in the PR; screenshots help for UI changes

## CI

[.github/workflows/build.yml](.github/workflows/build.yml) runs on:

- pull requests targeting `main`: **only `go test` and `go vet`**, no build
- pushes to `main`: tests and static checks only, as a post-merge safety net
- pushes of `v*` tags: tests, then builds Windows amd64 / arm64 and creates a Release
- manual `workflow_dispatch`: tests, then builds without releasing

Tests and static checks run once on `windows-latest` (amd64), and the build job waits for them to pass. PR checks are a safety net; still run the commands above locally before opening a PR.

## Contributing interface docs

Interface docs are as welcome as code, especially filling in the "unverified" gaps. Existing docs live in [docs/接口文档/](docs/接口文档/).

Before submitting, make sure:

- **Base every change on real packet captures or page source**; do not guess fields
- Follow the structure of the existing docs: request flow, request and response, status tables, implementation notes, and an "unverified" list at the end
- Replace real phone numbers, accounts, cookies, tokens, course IDs, course names, activity IDs, and assignment titles with placeholders; redact before exporting
- When a platform change breaks a doc, update it directly and describe how and when you verified it in the PR
- For a new platform, open an issue first and confirm the integration before writing docs

Use `docs(接口): ...` as the commit prefix.

## Release process

**Maintainers only.** A stable release follows these steps:

1. Cut a `chore/release-X.Y.Z` branch from the latest `main`
2. Update all four version locations:
   - `const Version` in `cmd/app/app.go`
   - the version badge at the top of `README.md`
   - the version badge at the top of `README.en.md`
   - `INFO_PRODUCTVERSION` and `INSTALLER_FILE_VERSION` in `build/windows/installer/project.nsi` (the latter must be four segments, `X.Y.Z.0`)
3. Commit `chore(发布): 版本号改为 X.Y.Z`, open a PR, merge with Rebase and merge, and delete the branch
4. Tag the tip of `main` and push:

   ```bash
   git tag -a vX.Y.Z -m "Catcher X.Y.Z"
   git push origin vX.Y.Z
   ```

5. CI verifies that the tag matches `Version` in `app.go`, then builds and creates a Release with `Catcher-windows-amd64.zip` and `Catcher-windows-arm64.zip`
6. CI **currently does not build the NSIS installer**. Build it locally when needed and upload it manually:

   ```bash
   wails build -nsis -installscope user
   mkdir -p build/release
   mv build/bin/Catcher-amd64-installer.exe build/release/Catcher-X.Y.Z-amd64-installer.exe
   gh release upload vX.Y.Z build/release/Catcher-X.Y.Z-amd64-installer.exe
   ```

Notes:

- Stable tags **must not contain `-`** (use `v1.3.0`, not `v1.3.0-final`). Otherwise CI marks the release as a pre-release, `releases/latest` cannot find it, and clients will not be prompted to update
- Tag and `Version` in `cmd/app/app.go` mismatch makes **CI fail outright**
- Before releasing, use `git grep` to search for the old version number and confirm all four locations were updated
- Hotfixes also start from `main` as `fix/<description>`, merge through the normal flow, and then get a patch version tag; do not skip the PR

## Reporting security issues

**Do not open a public issue**. Report privately through the repository's **Security → Report a vulnerability** entry. If that is unavailable, open an issue without sensitive details and ask for a private channel.
