## 调用流程

学习通支持两种登录方式。两条链路都已实测，拿到会话后进入同一套数据接口：

```text
① 登录（二选一）
   A. 手机号 + 密码  POST   passport2.xuexitong.com/fanyalogin
   B. 扫码           v8.chaoxing.com 自己的链路（见 ①B）
② 课程列表  GET   mooc1-api.chaoxing.com/mycourse/backclazzdata?view=json&rss=1
③ 作业列表  GET   mooc1-api.chaoxing.com/work/stu-work?ut=s
④ 作业详情  GET   mooc1-api.chaoxing.com/mooc-ans/android/mtaskmsgspecial?<参数取自 ③>
```

**域名分裂**：密码登录在 `passport2.xuexitong.com`，扫码入口在 `v8.chaoxing.com`，
数据全在 `mooc1-api.chaoxing.com`。两条登录链路只在「拿会话」这一步不同，
②③④ 与 cookie 表完全共用。
一次抓取需要走完 ①→④，② 的响应兼作登录态判定。

## 会话与请求头

### 公共请求头

| Header | 必填 | 值 | 说明 |
| --- | --- | --- | --- |
| `User-Agent` | 是 | 浏览器 UA | 学习通会拦截 Go 默认 UA，缺失时登录会被 302 到错误页 |
| `X-Requested-With` | 仅 ①B-3 | `XMLHttpRequest` | 轮询扫码状态时带 |
| `Content-Type` | 按接口 | `application/x-www-form-urlencoded` | 见各接口卡片 |

### Cookie

| 名称 | 域 | 路径 | HttpOnly | 必填 | 用途 |
| --- | --- | --- | --- | --- | --- |
| `JSESSIONID` | `passport2.chaoxing.com`（host-only） | 未验证 | 是 | 是（扫码链路） | 取图与轮询必须带同一个，丢了返回 `type=2` |
| `route` | 未验证 | 未验证 | 未验证 | 是（扫码链路） | `cloudscanlogin` 下发 |
| `UID` | 未逐项验证 | 未逐项验证 | 未逐项验证 | 未逐项验证 | 登录后下发 |
| `_uid` | 未逐项验证 | 未逐项验证 | 未逐项验证 | 未逐项验证 | 登录后下发 |
| `cx_p_token` | 未逐项验证 | 未逐项验证 | 未逐项验证 | 未逐项验证 | 登录后下发 |
| `uf` `xxtenc` `_d` `fid` `source` `tl` | 未逐项验证 | 未逐项验证 | 未逐项验证 | 未逐项验证 | 登录后下发 |
| `DSSTASH_LOG` `spaceFid` `spaceRoleId` `space_version` | 未逐项验证 | 未逐项验证 | 未逐项验证 | 未逐项验证 | 登录后下发 |

> 这只是常见的一组，实际上要**无脑累积全部 `Set-Cookie`**，不挑名字、不硬编码。
>
> `JSESSIONID` 是 **host-only**，不能用浏览器导出的 Cookie 字符串，也不要靠 cookiejar 跨域带。

### 登录态判定

读 ② 的顶层 `result`：

| 值 | 含义 |
| --- | --- |
| `1` | 已登录 |
| `0` | 会话失效（`msg` 含「请重新登录」） |

⚠️ **不要用 HTTP 状态码或响应字节数判定。** 会话失效时的真实形态是
**200 + 登录页 HTML + 0 个作业骨架** —— 只看状态码就会当成「抓到了，只是没作业」。

<a id="login-password"></a>

### ①A 密码登录 `实测`

**前置条件**：无

**请求**

```http
POST https://passport2.xuexitong.com/fanyalogin
Content-Type: application/x-www-form-urlencoded
User-Agent: <浏览器 UA>
```

**参数**

| 参数 | 位置 | 类型 | 必填 | 说明 | 示例 |
| --- | --- | --- | --- | --- | --- |
| `fid` | body | string | 固定 | 登录标识 | `-1` |
| `uname` | body | string | 是 | 手机号（11 位），AES 加密后 | `<encrypted>` |
| `password` | body | string | 是 | 密码，AES 加密后 | `<encrypted>` |
| `refer` | body | string | 固定 | 跳转来源 | `https://i.xuexitong.com` |
| `t` | body | string | 固定 | 固定值 | `true` |
| `forbidotherlogin` | body | string | 固定 | 禁止多设备登录 | `0` |
| `validate` | body | string | 固定 | 空串 | 空 |
| `doubleFactorLogin` | body | string | 固定 | 双因素登录开关 | `0` |
| `independentId` | body | string | 固定 | 独立账号 ID | `0` |
| `independentNameId` | body | string | 固定 | 独立账号名 ID | `0` |

**加密**

`AES-128-CBC + PKCS7 + Base64`，明文就是原文（不做 JSON 包装之类）。

| 项 | 值 |
| --- | --- |
| 密钥 | `u2oh6Vu^HWe4_AES` |
| IV | **= 密钥本身**（不是随机 IV） |

**响应**

```json
{ "status": true }
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | bool | `true` 表示登录成功 |
| `msg2` | string | 失败原因；成功时不返回 |

**失败形态**

| 场景 | HTTP | 业务码 / 页面特征 | 处理 |
| --- | --- | --- | --- |
| 账号或密码错误 | 200 | `status: false`，读 `msg2` | 报错；服务端对「账号错」和「密码错」返回同一句话 |
| 账号形态错误 | 200 | 同上 | 客户端先校验 11 位手机号，避免误导性提示 |
| 默认 UA | 302 | 跳到错误页 | 所有请求带浏览器 UA |

**注意**

- 密码登录不是一次 POST 就完事，中间会经过多次 302 重定向。必须**手工跟踪完整条 302 链（≤10 跳），逐跳收 `Set-Cookie`**，变成一个 cookie 集合。
- 别用 cookiejar：曲奇罐子会按域名、路径、host-only 规则自动过滤，`JSESSIONID` 会在跨域时丢掉。
- 前端可以加一句「请输入手机号」：学习通的账号是**手机号 + 密码**登录的。

**curl 示例**

```bash
curl -i 'https://passport2.xuexitong.com/fanyalogin' \
  -H 'User-Agent: Mozilla/5.0 ...' \
  --data-urlencode 'fid=-1' \
  --data-urlencode 'uname=<AES 加密后的手机号>' \
  --data-urlencode 'password=<AES 加密后的密码>' \
  --data-urlencode 'refer=https://i.xuexitong.com' \
  --data-urlencode 't=true' \
  --data-urlencode 'forbidotherlogin=0' \
  --data-urlencode 'validate=' \
  --data-urlencode 'doubleFactorLogin=0' \
  --data-urlencode 'independentId=0' \
  --data-urlencode 'independentNameId=0'
```

### ①B 扫码登录（v8.chaoxing.com） `实测（部分源码）`

> **状态：已实现并实测（2026-10-26）。** 取码、轮询、等待 / 失效 / 参数错误三种响应来自
> curl 实测；扫码成功链路已在桌面端用真实手机跑通（cookie 由 `pcrefer` 落地页补齐）。
> 「已扫码 / 取消」两个分支仍只有 `cloudscanlogin` 页面源码依据，未用真机触发。

**前置条件**：无

**与密码登录的关系**

学习通同时支持「手机号 + 密码」和「扫码」两种登录。密码链路已实测（见 ①A），
扫码入口在新版 Web 端 `v8.chaoxing.com`。两条链路只是在「拿会话」这一步不同。

**已确认（2026-10-26）**：扫码成功后下发的就是同一套 `chaoxing.com` cookie，
名字与密码登录一致（`UID` / `_uid` / `cx_p_token` / `uf` / `xxtenc` 等）。
所以 ②③④ 与密码登录完全共用，适配器只需要新增 `BeginQR` / `PollQR`，
`Session.Secret` 仍然存 cookie 表，不需要另算 Bearer token。

**整条链路**

扫码登录全部发生在 `passport2.chaoxing.com` 的 `cloudscanlogin` 页面里，
顶层 `v8.chaoxing.com` 只负责把 iframe 嵌进来。四步：

```text
GET  /cloudscanlogin?...          → HTML，含 uuid / enc，下发 JSESSIONID
GET  /createqr?uuid=...           → 二维码图片（PNG）
POST /getauthstatus  （每 3 秒）   → JSON，status / type / mes
成功 → iframe 把顶层跳到 pcrefer
```

#### ①B-1 打开扫码页 `实测`

**前置条件**：无

**请求**

```http
GET https://passport2.chaoxing.com/cloudscanlogin
    ?mobiletip=电脑端登录确认
    &time=<毫秒时间戳>
    &pcrefer=https://v1.chaoxing.com/backSchool/toLogin?source=num8
User-Agent: <浏览器 UA>
```

**参数**

| 参数 | 位置 | 类型 | 必填 | 说明 | 示例 |
| --- | --- | --- | --- | --- | --- |
| `mobiletip` | query | string | 否 | 二维码文案 | `电脑端登录确认` |
| `time` | query | string | 是 | 缓存破坏参数，填当前毫秒 | `1793199123196` |
| `pcrefer` | query | string | 是 | 登录成功后的落地页 | `https://v1.chaoxing.com/backSchool/toLogin?source=num8` |

**响应**

HTML。页面里有两个隐藏 input，轮询要用：

```html
<input type="hidden" id="uuid" value="<32 位十六进制>">
<input type="hidden" id="enc"  value="<32 位十六进制>">
```

| 字段 | 位置 | 提取规则 |
| --- | --- | --- |
| `uuid` | 隐藏 input | `id="uuid"` 的 `value` |
| `enc` | 隐藏 input | `id="enc"` 的 `value` |
| `route` | `Set-Cookie` | 累积 |
| `JSESSIONID` | `Set-Cookie` | 累积；HttpOnly |

**失败形态**

| 场景 | HTTP | 业务码 / 页面特征 | 处理 |
| --- | --- | --- | --- |
| 用 POST 打开 | 302 | 跳到 `passport2-api.chaoxing.com/views/error/passport404.html` | 必须用 GET |
| 后续请求丢了 `JSESSIONID` | 200 | 轮询返回 `type=2` | 取图与轮询必须带同一个 |

**注意**

- `time` 只是缓存破坏参数；`pcrefer` 是登录成功后的落地页；`mobiletip` 只影响二维码文案。
- `JSESSIONID` 是整条链路的会话凭证：取图和轮询都必须带同一个，丢了就返回 `type=2`。

**curl 示例**

```bash
curl -i 'https://passport2.chaoxing.com/cloudscanlogin?mobiletip=%E7%94%B5%E8%84%91%E7%AB%AF%E7%99%BB%E5%BD%95%E7%A1%AE%E8%AE%A4&time=1793199123196&pcrefer=https%3A%2F%2Fv1.chaoxing.com%2FbackSchool%2FtoLogin%3Fsource%3Dnum8' \
  -H 'User-Agent: Mozilla/5.0 ...'
```

#### ①B-2 取二维码图片 `实测`

**前置条件**：已打开扫码页，持有 ①B-1 的 `JSESSIONID` 和 `uuid`

**请求**

```http
GET https://passport2.chaoxing.com/createqr
    ?uuid=<uuid>&xxtrefer=&type=1&clientid=&fid=
Cookie: JSESSIONID=<...>; route=<...>
User-Agent: <浏览器 UA>
```

**参数**

| 参数 | 位置 | 类型 | 必填 | 说明 | 示例 |
| --- | --- | --- | --- | --- | --- |
| `uuid` | query | string | 是 | ①B-1 取到的 uuid | `<32 位十六进制>` |
| `xxtrefer` | query | string | 否 | 空串 | 空 |
| `type` | query | int | 是 | `1` 普通扫码；`2` 智慧课堂 | `1` |
| `clientid` | query | string | 否 | 空串 | 空 |
| `fid` | query | string | 否 | 空串 | 空 |

**响应**

| 项 | 值 |
| --- | --- |
| HTTP | 200 |
| 图片 | 270×270 的 1-bit 灰度 PNG |
| `Content-Type` | `image/jpeg`（**谎报，不要信**） |

**失败形态**

| 场景 | HTTP | 业务码 / 页面特征 | 处理 |
| --- | --- | --- | --- |
| 不带 ①B-1 的 cookie | 302 | 跳到 404 页 | 必须带同一个 `JSESSIONID` |

**注意**

- `type=1` 是普通扫码；页面检测到 `chaoxing_wisdomclass` UA 时改成 `type=2`（智慧课堂）。
- 二维码内容不用解析，直接把图片交给前端渲染。

<a id="qr-poll"></a>

#### ①B-3 轮询扫码状态 `实测`

**前置条件**：已打开扫码页，持有 ①B-1 的 `JSESSIONID`、`uuid`、`enc`

**请求**

```http
POST https://passport2.chaoxing.com/getauthstatus
Content-Type: application/x-www-form-urlencoded
X-Requested-With: XMLHttpRequest
Cookie: JSESSIONID=<...>; route=<...>
User-Agent: <浏览器 UA>

enc=<enc>&uuid=<uuid>
```

**参数**

| 参数 | 位置 | 类型 | 必填 | 说明 | 示例 |
| --- | --- | --- | --- | --- | --- |
| `enc` | body | string | 是 | ①B-1 取到的 enc | `<32 位十六进制>` |
| `uuid` | body | string | 是 | ①B-1 取到的 uuid | `<32 位十六进制>` |

**响应**

`Content-Type` 是 `text/html;charset=utf-8`，**正文其实是 JSON**，不要按 HTML 处理。
`type` 是**字符串**，按字符串解析更稳。

状态表（`mes` 为实测原文）：

| status | type | mes | 含义 | 来源 |
| --- | --- | --- | --- | --- |
| `false` | `"3"` | 未登录 | 等待扫码 | 实测 |
| `false` | `"4"` | —（带 `nickname` / `uid`） | 已扫码，等待手机确认 | 页面源码 |
| `false` | `"6"` | — | 用户在手机上取消登录 | 页面源码 |
| `false` | `"2"` | 会话已失效，请刷新页面重试 | 二维码 / 会话失效 | 实测 |
| `false` | `"1"` | 验证失败 | `enc` / `uuid` 不匹配 | 实测 |
| `true` | 未知 | — | 登录成功 | 页面源码 |

**失败形态**

| 场景 | 表现 | 处理 |
| --- | --- | --- |
| `type="1"` | 页面本身不处理，会一直轮询到 150 秒 | Go 侧直接报错，不要静默等待 |
| `type="2"` | 页面 `location.reload()` 换码 | 客户端回到取码 |
| `type="6"` | 用户取消，页面 `location.reload()` | 客户端回到取码 |

**注意**

- 页面每 **3000ms** 调一次，最多 **50 次**（约 150 秒）后显示「二维码已失效」。
- `type="4"` 时响应里有 `nickname`、`uid`，可用于前端显示「XXX 已扫码」。
- 不要按 `Content-Type` 判断响应：这个接口谎报 `text/html`。

<a id="qr-landing"></a>

#### ①B-4 落地与换会话 `实测（部分未证实）`

**前置条件**：①B-3 返回 `status: true`

**请求**

```http
GET <①B-1 的 pcrefer>
Cookie: <①B-3 之后累积的 cookie>
User-Agent: <浏览器 UA>
```

**参数**

无。`pcrefer` 的完整值来自 ①B-1，例如：

```text
https://v1.chaoxing.com/backSchool/toLogin?source=num8
```

**跳转链**

```text
https://v1.chaoxing.com/backSchool/toLogin?source=num8
https://v1.chaoxing.com/manage?ws=
https://i.chaoxing.com/base?t=<毫秒时间戳>
```

**响应**

| 项 | 值 |
| --- | --- |
| HTTP | 302 / 200，按跳转链逐跳跟随 |
| Cookie | 逐跳累积；登录后可见的名字见下 |
| 登录态 | 用 ② 的 `result` 验证 |

登录后 `document.cookie` 里能看到的 cookie 名字（只有名字，没有值）：

```text
UID  _uid  cx_p_token  uf  xxtenc  _d  fid  route  source  tl
DSSTASH_LOG  spaceFid  spaceRoleId  space_version
```

**失败形态**

| 场景 | 表现 | 处理 |
| --- | --- | --- |
| ①B-3 已成功但 cookie 不完整 | ② 的 `result` 为 `0` | 按登录失败处理，不要返回空列表 |

**注意**

- **未确认**：成功那一刻的 `getauthstatus` 响应本身有没有 `Set-Cookie`，还是必须跟
  `pcrefer` 才下发。实现时两边都收：先累积轮询响应的 `Set-Cookie`，再手动跟随
  `pcrefer`（sender 不自动跟 302）累积，最后用 ② 的课程列表 `result` 验证。
- `result` 不是登录态就按失败处理。
- 两条登录链路只在「拿会话」这一步不同，②③④ 与密码登录完全共用。

**①B 实现要点**

- `BeginQR` 要为每张码保存 `uuid`、`enc` 和同一个 cookie 表（至少 `JSESSIONID`、`route`），
  交给 `PollQR` 继续用；到达终态（成功 / 失效 / 取消 / 报错）后清理，避免内存泄漏。
- 状态映射用**字符串**比较：`"3"` → waiting，`"4"` → scanned，`"2"` → expired，
  `"6"` → failed（用户取消），`"1"` → 直接报错；`status: true` → succeeded。
  认不出的组合返回错误或 `unknown`，不能默认成「已登录」。
- 二维码图片以 `data:image/png;base64,...` 放进 `QRChallenge.Content`；
  前端遇到 `data:image/` 前缀时直接当图片用，否则仍走 `qrcode` 渲染。
- 轮询间隔 3 秒、上限 50 次（150 秒）；到期由客户端停止并回到 `QRExpired`，
  不要等页面自己 reload。
- 成功后先收 `getauthstatus` 的 `Set-Cookie`，再手动跟随 `pcrefer` 收一次，
  最后用 ② 的课程列表 `result` 验证登录态；两处 cookie 都**无脑累积**，不按名字硬编码。

### ② 课程列表（兼登录态判定） `实测`

**前置条件**：已登录，持有登录后的 cookie 表

**请求**

```http
GET https://mooc1-api.chaoxing.com/mycourse/backclazzdata?view=json&rss=1
User-Agent: <浏览器 UA>
Cookie: UID=<...>; _uid=<...>; cx_p_token=<...>; ...
```

**参数**

| 参数 | 位置 | 类型 | 必填 | 说明 | 示例 |
| --- | --- | --- | --- | --- | --- |
| `view` | query | string | 固定 | 返回 JSON | `json` |
| `rss` | query | string | 固定 | 固定值 | `1` |

**响应**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `result` | int | `1` 已登录；`0` 会话失效 |
| `msg` | string | `result=0` 时含「请重新登录」 |
| `channelList[]` | array | 班次 / 课程分组 |
| `channelList[].content.id` | int64 | classId（一个 channel 就是一个班） |
| `channelList[].content.cpi` | int64 | cpi，拼课程主页要用 |
| `channelList[].content.course.data[].id` | int64 | courseId |
| `channelList[].content.course.data[].name` | string | 完整课程名 |

**失败形态**

| 场景 | HTTP | 业务码 / 页面特征 | 处理 |
| --- | --- | --- | --- |
| 会话失效 | 200 | 登录页 HTML，`result` 不是 `1`，作业骨架为 0 | 按登录失效处理，不要返回空列表 |
| 课程数为 0 | 200 | `result: 1`，`channelList` 为空 | 不据此判登录态；只认 `result` |

**注意**

- ⚠️ **不要用 HTTP 状态码或响应字节数判定登录态。** 会话失效时的真实形态是
  **200 + 登录页 HTML + 0 个作业骨架** —— 只看状态码就会当成「抓到了，只是没作业」。
- 作业列表页的课程名**全被截断**，必须在这里补全。取
  `channelList[].content.course.data[].{id → name}`，其中 `id` 就是作业列表里的 `courseId`。
- **`courseId` 是稳定主键，课程名不是。** 去重、关联一律用 `courseId`。
- **课程总数会变，别当常量。** 它不能用作登录态或完整性的判据 —— 判定只认 `result`。
- **这里 `id` 是 JSON 数字，必须按原始字面量取，不能过 float64。**
  `100000003` 解成 `float64` 再格式化得到 `"1.00000003e+08"`，与作业列表页里的
  `"100000003"` 永远匹配不上，课程名会**静默**退回截断态。
- 这条不只是显示问题：课程名是去重主键的输入，截断名会让数据对不上。
- 班次信息挂在 `channelList[].content` 上，**不在** `course.data` 里；一个 channel 下的所有课程共用同一个 classId / cpi。两者同样是 JSON 数字，按原始字面量取；服务端给空时是 `"0"`，按缺失处理。

截断情况示例：

| `courseId` | 列表页给的 | 补全后 |
| --- | --- | --- |
| `100000001` | `某门课程A...` | 某门课程A（上） |
| `100000002` | `某门课程B(...` | **某门课程B（下）** |
| `100000003` | `某门课程C...` | 某门课程C（上） |

**请求**

GET https://mooc1-api.chaoxing.com/mooc-ans/android/mtaskmsgspecial

**参数**

| --- | --- | --- | --- | --- | --- |
| `taskrefId` | query | int64 | 是 | 取自 ③ 的 `data` URL | `<taskrefId>` |
| `msgId` | query | int | 固定 | 固定 `0` | `0` |
| `courseId` | query | int64 | 是 | 取自 ③ 的 `data` URL | `<courseId>` |
| `userId` | query | int64 | 是 | 取自 ③ 的 `data` URL | `<userId>` |
| `clazzId` | query | int64 | 是 | 取自 ③ 的 `data` URL | `<clazzId>` |
| `type` | query | string | 固定 | `work` | `work` |
| `enc_task` | query | string | 是 | 取自 ③ 的 `data` URL | `<enc_task>` |

**响应**

这个 Android 接口路径会 **302** 到 H5 详情页：

```text
…/mooc-ans/work/phone/task-work?taskrefId=…&courseId=…&classId=…&enc_task=…
```

截止时间在**跳转后的页面**里。

| 内容 | 位置 | 提取规则 |
| --- | --- | --- |
| 跳转地址 | HTTP `Location` | 302 → `/mooc-ans/work/phone/task-work?...` |
| 截止时间（展示） | `<h4>截止时间：09-25 22:55</h4>` | 解析月-日 时:分 |
| 截止时间（机器可读） | `<span aria-label="截止时间09月25日22时55分18秒">` | 解析月日时分秒 |
| 登录失效 | `Location` 指向 `passport2.chaoxing.com/login` | 会话失效 |

**失败形态**

| 场景 | HTTP | 业务码 / 页面特征 | 处理 |
| --- | --- | --- | --- |
| 正常详情 | 302 | `Location` 指向 `work/phone/task-work` | **正常跳转，继续跟随** |
| 会话失效 | 302 | `Location` 指向 `passport2.chaoxing.com/login` | 按登录失效处理 |
| 其他 3xx | 302 | 其他 `Location` | 逐跳跟随；只有 `passport2` 登录页才算失效 |

> **实测记录（2026-10-22，真实账号）**：这个 Android 接口路径会 **302** 到 H5 详情页，
> 截止时间在**跳转后的页面**里。302 是正常跳转，不是登录失效；
> 只有跳到 `passport2.chaoxing.com/login` 才算会话失效。
> 原来的实现把所有 3xx 都当 `ErrAuthExpired`，导致每条作业详情都失败、整次抓取报「登录已失效」。

**注意**

- 详情页逐条间隔 **250ms**。
- 详情页没有年份，年份按下面的规则补全。
- 标题里的日期不是截止时间；「已完成」条目常常拿不到截止时间。

#### 截止时间与年份补全

页面里的两处截止时间都**没有年份**：

```html
<h4>截止时间：09-25 22:55</h4>
<span aria-label="截止时间09月25日22时55分18秒"></span>
```

| 条目类型 | 数据来源 | 规则 |
| --- | --- | --- |
| 进行中（`aria-label` 有「剩余时间」段） | 列表页的剩余时间 —— **唯一带绝对信息的源** | `now + 剩余`，再用详情页的月-日交叉校验；偏差 ≤10 分钟时用详情页的秒级时刻（剩余时间只到分钟） |
| 已截止（无「剩余时间」段） | 详情页的月-日 | 月-日 > 今天 → 归去年；否则归今年 |

剩余时间解析：`(\d+)\s*(天|小时|分钟)` 三段相加。

示例：

| 条目 | 剩余 | 详情页 | 结果 |
| --- | --- | --- | --- |
| 第一次作业（进行中） | `312小时55分钟` | `09-25 22:55` | `09-25 22:55` ✅ 吻合 |
| 某次补交作业（已截止） | — | `06-23 23:00` | `2026-06-23` |
| 某次期末补交作业（已截止） | — | `06-25 23:59` | `2026-06-25` |

> ⚠️ 注意一下：
>
> **不要用标题里的日期当截止时间。** 比如「某次作业…**20260622**」的详情页截止实际是 `06-23 23:00`。
>
> **剩余时间是相对值**，必须当场换算成绝对时刻再落盘。
>
> **「已完成」条目常常拿不到截止时间。** 但是无所谓，我们要抓取得反正是没有完成的😋

## 解析规则

### 走 `aria-label`，不要走 class 选择器

**状态与剩余时间只从 `aria-label` 取。class 选择器覆盖不全：**

- `class="status"` —— **只出现在「未提交」条目上**；已完成条目是裸的
  `<span aria-hidden="true">已完成</span>`
- `class="fr"`（剩余时间）—— **只出现在「进行中」条目上**

按 class 解析的后果不是报错，而是**静默读空**：状态变成空字符串，剩余时间也拿不到 ——
而剩余时间是唯一能定出年份的信息源，于是大部分条目的截止时间都算不出来。
一个 DDL 工具却大面积没有截止时间，且全程不报错。

`aria-label` 格式（后两段可能不存在）：

```text
作业名称<标题>作业状态<状态>所属课程<课程>剩余时间<剩余>
```

> ⚠️ **三个定界符要从右往左找（`LastIndex`）**，不能从左往右。标题是自由文本，可能自带日期、
> 全角括号、空格（例如 `某次作业 （括号里是补充说明）20260622`），
> 理论上也可能自带「作业状态」这类字样；而真正的定界符一定排在标题**之后**。
> 从左找会被标题里的同名字样锚错。

### 三态 = 两个独立维度交叉

| 维度 | 来源 |
| --- | --- |
| **交没交** | `aria-label` 的「作业状态」段：`未提交` / `已完成` / `待批阅` |
| **还在不在跑** | 图标文件名：`task-work.png` 进行中 / `task-work-gray.png` 已结束 |

| 进行中 | 已提交 | 阶段 | 处理 |
| --- | --- | --- | --- |
| 是 | 否 | 未到期 | 提醒 |
| 否 | 否 | **已截止未提交** | **最该提醒** |
| 否 | 是 | 已完成 | 忽略 |

> **实测记录（2026-10-22，真实账号）**：「作业状态」还会出现 `待批阅` —— 学生已交、老师还没批改，属于**已提交**。真实列表里它很常见（实测约占三成），接口文档原来的两个值覆盖不全。
> 不认它会有两个后果：误报成「状态未知」，以及给已交作业多打一遍详情请求。
> 其余仍认不出的状态（比如 `已过期`）继续保持 `unknown` + warning。
>
> ⚠️ **认不出的状态要显式暴露，不许默认成「已完成」。** 静默当已交 = 悄悄漏掉未交的作业，
> 是本模块最容易犯的错。
>
> ⚠️ **不要用 `redPoint` 分类。** 它是「**未读**」标记，不是「未交」：**随阅读清除**。
> 刚进页面能看到，看过一遍之后就没了 —— 拿它当判据等于「只要用户打开过平台，就全部漏掉」。

## 实现要点

1. **手工维护 cookie 表**，不用 cookiejar；不用浏览器导出的 cookie 字符串。
2. **登录态看 `result`**，不看状态码 / 字节数。
3. **失败不许静默** —— 抓取失败必须与「真没作业」可区分（抛错，不返回空列表），
   否则界面分不清「今天没作业」和「登录挂了」。
4. **状态与剩余时间走 `aria-label`**，定界符从右往左锚 —— 按 class 解析会静默读空。
5. **`courseId` 按原始字面量取**，不过 float64 —— 否则课程名补全静默全失效，
   而课程名是去重主键的输入。
6. **认不出的状态显式暴露**，不许默认成「已完成」。
7. **详情页逐条间隔 250ms**。
8. **原始响应留底**，便于排查平台改版。
9. **发请求前校验账号形态**（11 位手机号）—— 服务端对「账号错」和「密码错」返回同一句话，
   不自己拦就只能看到误导性的「用户名或密码错误」。
10. **课程数、作业数都不当常量** —— 只认 `result` 判登录态；`haveMore` 读了再决定要不要翻页。
11. **去重主键用 `(用户, 平台, 课程, 标题)`，`deadline` 不参与** —— 改了算变更，不算新记录。
12. **扫码登录只替换「拿会话」这一步**（见 ①B）—— cookie 表与 ②③④ 和密码登录共用，**不要为扫码另写一套抓取😶‍🌫️**。
13. **作业跳转走课程主页** —— 手机版 `task-work` 不能提交，桌面 `dowork` 的 `standardEnc` 客户端拿不到；地址只用 ② 的字段拼，不额外发请求。
14. **所有请求带浏览器 `User-Agent`** —— 学习通会拦截 Go 默认 UA，缺失时登录被 302 到错误页。

### 复核方法（可选）

接口已经从页面源码和 curl 里拿到了，正常不需要再抓包。之后要复核「已扫码 / 取消 / 成功」
三种状态的真实响应时，用浏览器在 `passport2.chaoxing.com` 这个跨域 iframe 里录制：

- 脚本在 `document-start` 运行，并确认它在 iframe 里也跑了。
- 扫码成功会整页跳走，脚本要能自动保存。
- 只记录状态码、主机、响应体积与打码后的字段，不记录 cookie 值。
- 导出前默认打码 cookie、token、`enc`、手机号等值，只保留字段名与状态值；
  **不要把未打码的导出结果贴到对话或提交进仓库。**

顶层收不到子 frame 上报时，把下面这个地址单独开一个标签页（`time` 用页面里的值），
