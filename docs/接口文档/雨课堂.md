# 雨课堂（yuketang）接口文档

前言：
我拿了我自己的账号扫码测试的（适用于**长江雨课堂**，其他的我没有做😶‍🌫️）

---

## 调用流程

```text
① 取二维码  GET   changjiang.yuketang.cn/api/v3/user/login/app-web-pre-info
② 轮询确认  POST  changjiang.yuketang.cn/api/v3/user/login/app-web-login
③ 换取会话  POST  changjiang.yuketang.cn/pc/web_login
④ 课程列表  GET   changjiang.yuketang.cn/v/course_meta/learning_list/
⑤ 作业列表  GET   changjiang.yuketang.cn/v/course_meta/classroom_logs?<参数取自 ④>
```

**域名不分裂** —— 五步全在 `changjiang.yuketang.cn` 一个域下

**①→③ 是一次性登录**，拿到 `sessionid` 后存起来即可（实测能活 **3 天**）。
日常抓取只走 **④→⑤** 两步，所以真正要经常跑的只有后面那两步

> **登录方式是微信扫码，不是账密。** 程序要在终端/界面渲染一个二维码，用户拿微信或「雨豆 App」扫
> 全程纯 HTTP，**不需要密码、不需要统一认证、不需要人工粘 Cookie**

## ① 取二维码

```text
GET https://changjiang.yuketang.cn/api/v3/user/login/app-web-pre-info
```

**无需任何请求头、无参数、无 Cookie。** 实测连 `Accept` 都不带也能拿到（和带头的响应同为 388 字节）

### 响应：二维码信息

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "qrContent": "https://changjiang.yuketang.cn/api/v3/user/login/app-web-qr?u={UUID}&t=1789526487&s={SIGN}&v=1",
    "qrImage": "",
    "token": "eyJ…"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `qrContent` | string | **一个 URL**，二维码要自己拿它渲染 |
| `qrImage` | string | **恒为空串** —— 服务端不给图片，别指望它😡 |
| `token` | string | JWT，**5 分钟**有效，给 ② 用 |

### 关于 `token`

解出来是这样：

```json
{ "id": "{UUID}", "iat": 1789526487, "exp": 1789526787 }
```

`exp - iat = 300` 秒，**5 分钟**。

> 💡 `token` 里的 `id` **就是** `qrContent` 里 `u=` 那个 UUID，两者是同一个值。

**二维码渲染**：`qrContent` 就是个普通 URL，任何二维码库都行
用 `github.com/skip2/go-qrcode`就可以，如果要看这个二维码可以用 [这个网站](https://cli.im/text)

## ② 轮询扫码结果

```text
POST https://changjiang.yuketang.cn/api/v3/user/login/app-web-login
Content-Type: application/json
```

| 参数 | 值 |
| --- | --- |
| `token` | ① 给的 `token` |

请求体：

```json
{ "token": "eyJ0eXAiOiJKV1QiL…" }
```

轮询这个接口，直到扫码成功。

### 响应（三种形态，必须分开处理）

| 情况 | 响应 | 处理 |
| --- | --- | --- |
| **还没扫码** | **nginx 504**，HTML 页面 | **继续轮询，这不是错误** |
| **token 作废** | HTTP **400** + `{"code":50400,"msg":"BAD_REQUEST","data":null}` | 回 ① 换一张码 |
| **扫码成功** | HTTP 200 + `{"code":0,"data":{"UserID":…,"Auth":"…"}}` | 进 ③ |

**还没扫码** 时拿到的就是一个 nginx 的错误页：

```html
<html>
<head><title>504 Gateway Time-out</title></head>
<body>
<center><h1>504 Gateway Time-out</h1></center>
<hr><center>nginx</center>
</body>
</html>
```

**扫码成功** 时：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "UserID": {USER_ID},
    "Auth": "{AUTH_UUID}"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `UserID` | **number** | 用户 ID，**是数字不是字符串** —— 别过 float64 再格式化 |
| `Auth` | string | 36 字符 UUID，给 ③ 用 |

> ⚠️注意一下 **这一步拿到的还不是会话。** 别拿着 `UserID`/`Auth` 去调 ④，会失败。必须先走 ③
>
> **未扫码时服务端是「挂住」而不是「拒绝」** —— 请求会吊着，约 60 秒后由 nginx 以 504 切断
> 所以客户端超时必须设在 60s 以上（我对齐 server 行为用了 70s），
> 且**超时和 504 都要当成「继续等」**。否则用户还没掏出手机，程序就报错了

## ③ 换取会话

```text
POST https://changjiang.yuketang.cn/pc/web_login
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
```

请求体：

```json
{ "UserID": {USER_ID}, "Auth": "{AUTH_UUID}" }
```

> **注意：body 是 JSON，`Content-Type` 却声明成 form-urlencoded。**
> 它**不是** form 编码，也不是 `application/json`

### 解释

前端代码长这样：

```js
t.ajax({ url: "/pc/web_login", type: "post", data: (0,H.default)(Jt), dataType: "text", … })
```

`H.default` 追下去就是 **`JSON.stringify`**（压缩后的模块 364 → 365，
内容是 `(r.JSON&&r.JSON.stringify||JSON.stringify).apply(JSON,arguments)`）——
所以 body 确实是 JSON 字符串。

**但这里没写 `contentType`**，于是走 jQuery 默认的
`application/x-www-form-urlencoded; charset=UTF-8`。

同一个文件里的**密码登录**是显式声明 JSON 的，可以对比：

```js
data: (0,H.default)(e), contentType: "application/json"      // 账密登录
data: (0,H.default)(Jt)                                      // pc/web_login ← 没有 contentType
```

> 按 7 种组合（JSON body × 两种 CT × 带不带 Referer / 匿名 cookie）
> 逐个打过，**只有「JSON body + form CT」这一个能拿到 Cookie**，其余全返回登录页 HTML。
> 上面的 JS 分析是事后印证的 —— 平台改版时按这个矩阵重试即可。

### 响应：成功 JSON ／ 失败 HTML

| 结果 | 响应 |
| --- | --- |
| **成功** | **JSON**，同时下发 `Set-Cookie` |
| **失败** | **HTML 登录页**，正文里带 `data-status_code="401"` |

✅ **成功响应正文（2026-09-16 实测，67 字节）**：

```json
{ "data": {}, "success": true, "user_id": {USER_ID} , "user_role": -1 }
```

| 字段 | 说明 |
| --- | --- |
| `success` | **`true`** —— 前端就是拿它判成败 |
| `data` | **空对象 `{}`**，不是 `null`，也没有内容 |
| `user_id` | number，与 ② 的 `UserID` 同值 |
| `user_role` | `-1`（网页端学生账号） |

> ⛔ **正文里没有 `code` 字段。** 早先那句「从前端看它读 `t.code === 0 && t.data`，大概是 `{code:0,data:{…}}`」
> 是**把 ② 的代码当成了 ③ 的** —— `code===0 && t.data` 属于 `pc_web_login_confirm`（② app-web-login）。
> ③ 的调用点（`login.js`）是：
>
> `t.ajax({url:gt.default.pc_web_login, type:"post", data:(0,H.default)(Jt), dataType:"text", success:function(n,r){try{var o=JSON.parse(n);e&&e(o)}catch(e){t(".J_exit").trigger("click")}}, error:function(t,e,n){}})`
>
> 回调里接着判 `t.success && …` —— **判据是 `success`**，与实测正文吻合。

**判成败三条路，按可靠性排序**：

1. **有没有下发 `sessionid`** —— 最硬，与正文格式无关（**推荐**）
2. 正文能否 `JSON.parse` —— 前端就是这么判的（失败响应是 HTML，parse 必抛）
3. 正文 `success === true`

成功后一次性下发：

```text
Set-Cookie: login_type=WX
Set-Cookie: csrftoken={CSRFTOKEN}
Set-Cookie: sessionid={SESSIONID}
Set-Cookie: django_language=zh-cn
```

> 注意：**成功是 JSON，失败是 HTML。** 前端是用 `dataType:"text"` 加
> `try{JSON.parse}catch{}` 兜的 —— **别硬解 JSON**，解析失败说明那是失败响应，不是异常。

## 会话凭据与登录态判定

### 只要 `sessionid`

对同一份响应做减量对照：

```text
只带 sessionid                → 正常，抓到 34 门课
sessionid + csrftoken         → 正常，抓到 34 门课
其余全带、但没有 sessionid     → 失效
```

**`sessionid` 单独就充分且必要。** 其余 Cookie（`csrftoken` / `uv_id` / `university_id` /
`login_type` / `django_language`）在数据层用不到 —— **持久化时只存 `sessionid` 一个值就够了**。

> **不要用 cookiejar 了。** `sessionid` 在 `changjiang.yuketang.cn` 域签发，
> 标准 HTTP 客户端的 cookie 罐会因跨域把它丢掉。全程**手工读 `Set-Cookie`、手工拼 `Cookie` 头**。

请求时这样带：

```text
Cookie: sessionid={SESSIONID}
```

### 会话失效长什么样

**HTTP 状态码仍然是 200**，只能靠响应体的 `op` 字段判：

```json
{
  "url": "/web?next=/v/course_meta/learning_list/",
  "msg": "页面正在跳转，请稍候...",
  "op": "web_redirect"
}
```

> 这里注意一下，**只看状态码会把「登录已失效」当成「成功但没数据」。**
> 判据是 `op == "web_redirect"`，**不是 HTTP 200**。
> 这个形态在无 Cookie、无 sessionid、会话过期三种情况下**完全一样**。

### 会话能活多久

我感觉雨课堂的会话有效期应该挺长的🤔

| 样本 | 结果 |
| --- | --- |
| `sessionid` 自己声明的有效期 | `Max-Age=1209600` = **14 天**（**声明值，非实测**） |
| 浏览器导出、放置 **3 天**的会话 | 仍能正常抓到 34 门课 |
| 扫码得到的新会话 | +26 分钟 / +51 分钟 / **+2 小时 25 分** 三次复测均正常 |

**结论：会话应该是以天为单位。** 存起来复用完全可行，不必每次启动都扫码。

## ④ 课程列表

```text
GET https://changjiang.yuketang.cn/v/course_meta/learning_list/
```

**免任何自定义请求头**，只要 `Cookie: sessionid=…`。

### 响应：课程数组

```json
{
  "success": true,
  "data": [
    {
      "course_id": 1000001,
      "classroom_id": 20000001,
      "course_name": "某门课程",
      "classroom_name": "2026春-某门课程-1班",
      "university_id": 1001,
      "role": 5
    }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `course_name` | 课程名，**不带学期** |
| `classroom_name` | **带学期前缀**（如 `2026秋-…` / `2026春-…`） |
| `course_id` | 传给 ⑤ 的 `course_id=` |
| `classroom_id` | 传给 ⑤ 的 `classroom_id=` |
| `university_id` | 学校编号，**各校不同**（上例为占位值 `1001`，少数公共课为 `0`） |
| `role` | 学生 = `5` |

> **2026-10-22 实测补充**：真实响应只有 `{"data":[...]}`，**没有 `success` 字段**，`msg` 也没有。
> 实现在 JSON 解析后应把“字段缺失”当作成功，只有显式 `"success": false` 才报错；
> 另有 `classroom_top` / `teacher` / `university_mini_logo` 等未列出的字段，解析时忽略即可。
> **要过滤学期，看 `classroom_name`，不是 `course_name`。** 学期前缀只挂在前者上。
>
> 历史课也在列表里（比如我自己测试的时候，我的账号 34 门含大量已结课），不过滤会抓进一堆噪声。这里注意一下吧

## ⑤ 作业列表

```text
GET https://changjiang.yuketang.cn/v/course_meta/classroom_logs
    ?course_id={course_id}&classroom_id={classroom_id}&activity_type=-1
```

参数取自 ④。**同样免任何自定义请求头。**

### 响应结构

```json
{
  "success": true,
  "msg": "",
  "data": {
    "now_time": 1789271993,
    "activities": [
      [ { "id": 1, "type": 9,  "title": "…", "create_time": 1749000000 } ],
      [ { "id": 2, "type": 20, "title": "第七章练习1",
          "create_time": 1749000000,
          "content": { "score_d": 1751299199000, "leaf_id": 40000000 } } ]
    ]
  }
}
```

> **`activities` 是按日期分组的嵌套数组**（`[[…],[…]]`），不是平铺的。
> 直接 `.filter(a => a.type === 20)` 会**静默返回空**，必须先 `.flat()`。

**这条是实测复现的**（同一门课）：

```text
外层组数 = 18 ；摊平后 = 33 条
不摊平直接筛 type==20  →  0 条       ← 「静默返回空」当场复现
摊平后：type 9 → 13 条 ／ type 14 → 3 条 ／ type 20 → 17 条
```

> **失败形态极难发现**：HTTP **200**、`success: true`、`msg: ""` —— 只是列表空
> 没有任何一层会报错。不摊平的实现会**稳定地把「17 个作业」报成「没有作业」**

### 活动 `type` 枚举

| type | 含义 | 有 `content` | 有 `content.score_d` |
| --- | --- | --- | --- |
| `20` | **作业 / 考试**（旧编码） | ✅ 17/17 | ✅ 17/17 |
| `15` | **慕课视频学习任务**（旧编码） | ✅ | ✅（等于课堂 `class_end`） |
| `19` | **习题 / 练习 / 作业**（新编码） | ✅ 22/22 | 21/22（1 条是 `""`） |
| `17` | **视频学习任务**（新编码） | ✅ 9/9 | ✅ 9/9 |
| `9` | 通知（老师消息） | ❌ 0/13（连字段都没有） | ❌ |
| `14` | 授课记录 | ❌ 0/3（连字段都没有） | ❌ |
| `2` | 课件 / 章节（2026-10-25 实测） | ❌ | ❌ |

> ✅ **`content` 的存在性与 `type=20` 重合**（首个账号 17/17 机证）—— 判「是不是作业」看
> `content.score_d` 在不在，比看 `type` 更稳
>
> **2026-10-23 另一账号实测补充**：`type=15` 带 `content`，是**慕课视频学习任务**
> （标题「某门课程衔接课视频学习」）。它的 `content.score_d` 与该课堂的 `class_end`
> 完全相等（`1801411199000`），是**课程结束时间**，不是作业截止时间。
> 所以「`content` 只出现在 type=20」已被证伪。它仍是一条带期限的学习任务：
> 实现里保留、状态照旧 `unknown`，但不再作为未知类型告警
>
> **2026-10-25 用户账号实测（某门专业课）**：整门课 40 条活动里**没有一条
> `type=20/15`**，全是 `19`（22 条）/`17`（9 条）/`14`（6 条）/`2`（3 条）。
> 标题能一一对上：`19` 全是「课前预习习题 / 课后作业 / 课堂练习」，
> `17` 全是「课前预习视频」，`14` 是「X月X日授课」，`2` 是章节名。
> 所以**两套编码并存**，实现把 `19` 归为作业类、`17` 归为视频类，
> 不能再当未知类型告警
>
> ⚠️ **「作业**只**挂在 `type=20` 上」已被证伪。** 兜底照做：遇到**带 `content`
> 却不属于 9/14/15/17/19/20** 的 `type` 时记警告，不要静默丢弃

### 服务端时钟 `data.now_time`

| 项 | 值 |
| --- | --- |
| 样例 | `1789271993` → `2026-09-13 11:59:53` |
| 单位 | **秒**（10 位） |
| 含义 | **服务端当前时间**（不是业务数据） |

> **算截止时间时以它为准**

---

### 截止时间

#### 单位不一致 —— 同一个响应里两种单位

| 字段 | 单位 |
| --- | --- |
| `create_time` | **秒**（10 位） |
| `content.score_d` | **毫秒**（13 位） |

**实现必须做位数断言**（13 位才当毫秒）。拿错直接得到 1970 年。

实测位数分布（17 条 type=20 全量）：

```text
content.score_d   13 位 × 17/17    ← 全部毫秒
create_time       10 位 × 17/17    ← 全部秒
```

> 注意 **17/17 干净 ≠ 可以省掉断言。** 这 17 条全来自同一门课、同一学期，
> 且截止时刻全部相同 —— 是**高度同质的样本**。断言照做

### 而 `score_d` 就是截止时间

下面是结果情况：

通知（`type: 9`）的标题里常写死截止时间，这可以当作一种依据：

**5/5 全中，且条数对齐**：

| 通知写死的日期 | `score_d` 命中 | 通知原文（节选，章节主题已隐去） |
| --- | --- | --- |
| `03-31` | **3 条** | 第七章 …**章节练习1，练习2，练习3**…3月31号之前完成 |
| `04-15` | **3 条** | 第八章 …**章节练习1，练习2，练习3**…4月15日之前完成 |
| `05-18` | **3 条** | 第九章 …5月18日之前完成 |
| `05-26` | **3 条** | 第十章 …**章节练习1，练习2，练习3**…5月26号之前完成 |
| `06-09` | **3 条** | 第十一章 …**章节练习1，练习2，练习3**…6月9号之前完成 |

> 💡 **条数对齐比日期命中更有力**：通知说「练习1、2、3 三份」，`score_d` 就**恰好 3 条**
> 落在那天 —— 老师说的和接口给的是**同一批作业**
>
> **无反例**：`score_d` 解出的 7 个日期里，通知没提的只有 `04-23`（1 条）和 `06-16`（1 条，期末），
> 都不构成矛盾

**截止时刻全部落在 `23:59:59`** —— 17/17 无一例外（雨课堂统一设到当天最后一秒）。
通知里「6月9号」这种只精确到日的写法，正好被这条解释掉。

## 其他可用端点

### 课程详情（取 sign / sku）

### 章节树

```text

- 叶子的 `id` 等于 `classroom_logs` 里的 `content.leaf_id`，**可用来关联**

### 待办列表

GET .../c27/online_courseware/course/classroom/{cid}/{sku}/todo_list/?client_type=h5
```

- `data.count.total` 等于课程页上显示的「未完成 (N)」

### 请求头（`/mooc-api/` 与 `/c27/` 必需）

这两支要求**一整套七个头**，缺任何一条都返回：

```json
{"msg":"XTBZ IS REQUIRED","error_code":40000,"sub_code":400,"data":{},"success":false}
```

| 头 | 值 |
| --- | --- |
| `Accept` | `application/json, text/plain, */*` |
| `xtbz` | `ykt` |
| `Xt-Agent` | `web` |
| `X-Client` | `web` |
| `university-id` | 你的 `university_id`（上例 `1001`） |
| `uv-id` | 同上 |
| `classroom-id` | `{当前课程 classroom_id}` |

> ⚠️ **HTTP 状态码是 200。** 这是**业务层失败** —— 只看状态码会把失败当成「空数据」。
> 判断成败要读响应体的 `success` / `error_code`。
>
> 错误文案只提 `XTBZ`，但实际缺的是**整套** —— 只补 `xtbz` 试过 5 种取值，全部无效。
>
> 全部是 GET，**`X-CSRFToken` 不需要**。

### 判「头对不对」不能靠「没报错」

要拿**已知答案**对：

```text
GET .../mooc-api/v1/lms/learn/course/reset_leaf?sku_id={sku}
```

正确响应恒为 `{"data":[],"success":true}`。对上了，头就是对的；对不上，后面全是噪音。

## 实现要点

1. **登录走微信扫码** —— 纯 HTTP 可完成，不需要密码、不需要统一认证
2. **①→③ 只做一次，`sessionid` 持久化** —— 寿命小时~天级，不必每次启动都扫
3. **只要 `sessionid` 一个 Cookie**，且**不要用 cookiejar** —— 手工读 `Set-Cookie`、手工拼 `Cookie` 头
4. **③ 的 body 是 JSON、`Content-Type` 是 form-urlencoded** —— 最反直觉的一步，别"顺手修正"
5. **② 轮询超时设在 60s 以上，且把 504 和超时都当「继续等」** —— 未扫码时服务端是**挂住**不是拒绝
6. **③ 成功是 JSON、失败是 HTML** —— 别硬解 JSON；判成败看有没有下发 `sessionid`
7. **登录态看 `op == "web_redirect"`**，不看 HTTP 状态码 —— 失效时也是 200
8. **核心链路免头** —— 只抓作业 + 截止时间的话，别去碰 `/mooc-api/`，省掉整套请求头的坑
9. **`.flat()` 不能省** —— `activities` 是嵌套数组，不摊平会静默返回空
10. **`score_d` 断言 13 位**（`create_time` 断言 10 位）—— 单位不一致，拿错得到 1970 年
11. **判成败看响应体，不看 HTTP 状态码** —— 业务失败也是 200
12. **失败不许静默** —— 抓取失败必须与「真没作业」可区分（抛错，不返回空列表），
    否则界面分不清「今天没作业」和「登录挂了」
13. **「还剩几天」以 `data.now_time` 为基准**，不用本机时钟
14. **显式带 `Accept: application/json`** —— 同一端点有两个渲染器，默认可能拿到 HTML 美化页
15. **`UserID` 是数字，按原始字面量取**，不过 float64
16. **逐课间隔 300ms**（我的账号 34 门）
17. **原始响应留底**，便于排查平台改版
18. **过滤学期看 `classroom_name`** —— 学期前缀只挂在它上面，历史课也在列表里
19. **`Auth` 存下来、可重放** —— 会话失效时拿它直接重打 ③ 就能换到新 `sessionid`，**不必再扫码**。
    实测 11:01 扫码拿的 `Auth`，13:26 仍有效（**≥2 小时 25 分**，上界未测）
20. **新登录不会顶掉旧会话**（实测证伪）—— 同一账号多处登录互不影响，
    不会把用户的浏览器挤下线，不必为此加提示或做节流
21. **`content.score_d` 可能是空字符串** —— 2026-10-25 用户账号实测（某门专业课）：
    活动 `30000000`（`type=19`，某次课堂练习）的 `content.score_d` 是 `""`。
    用 `json.Number` 直接承接时，整段 `classroom_logs` 解码失败
    （`cannot unmarshal string "" into Go value of type json.Number`），
    整门课的作业一条都没入库。实现改用宽松数字类型，接受 `""` / 带引号数字 /
    `null`，空值降级成逐条 warning；作业类的 `score_d` 为空时保留作业、截止时间
    记为未知，不再静默丢弃
22. **活动类型按两套编码处理** —— `19`/`17` 与 `20`/`15` 并存，见上面的
    type 枚举。新增类型先看标题再归类，不要凭编码猜
23. **提交状态保持 `unknown`，不自动换算** —— `todo_list` 能按
    `leaf_id` 推算完成状态（2026-10-25 实测有效，规则见上），但平台只给
    「完成/未完成」，视频的「看完」又对不上「提交」，自动标状态容易误导。
    当前实现一律 `unknown`，由用户手动标记；以后要启用，别改变 `Complete`，
    否则会误触发软删除
